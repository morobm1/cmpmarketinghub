# Competitor Cards — Hot Fix Plan (4 targeted fixes)

Verified against the current `competitor_cards.html` implementation (post prior feature build). All four fixes are additive/corrective — no data model changes required (see F).

## A. Existing functions/classes/state to reuse

- **Buttons**: `.btn`, `.btn-primary`, `.btn-success`, `.btn-outline`, `.btn-accent`, `.btn-warning`, `.btn-sm`, `.btn-back`, `.subject-card-section .btn-subject` (lines ~62-75, 414-415).
- **Card grid**: `renderGrid()` inside `renderGallery()`, `.card-thumb`, `.thumb-img`, `.thumb-badges` / `.thumb-badges-right` (top-left/right badges, lines 104-105), `.thumb-body`, `.thumb-actions` (edit/duplicate/view/archive — lines 116-120).
- **Selection state**: `compareSelected` (global `{id:true}`, line 726) + `getCompareIds()` (line 896) — the single existing comparison-selection store, already shared by card checkboxes, `renderComparison()`, `renderRateComparison()`, and Amenity Cart. `reportSelected` is separate and must stay untouched/independent.
- **Property scoping**: `currentProperty` (global, active Our Property name) + `subjectCard` + `cards` (already loaded/scoped to `currentProperty` by `loadCards()`/`silentRefreshCards()`) — this is the existing, proven property-to-competitor relationship; no new fetch needed for Hot Fix 3.
- **Admin gating**: `currentUser.role === 'admin'` (already gates the "Bulk Update Images" button in `renderGallery()`).
- **List-row UI pattern**: `.report-card-list`, `.report-card-list-title`, `.report-card-item`, `.rci-name`, `.rci-type`, `.report-select-all` (lines 436-446) — built for Report Builder Step 1's competitor checklist; reuse directly for the new Rate Compare modal's competitor list instead of inventing new row markup.
- **Modal chrome precedent**: `mmp_admin.html` already defines `.modal-overlay/.modal/.modal-header/.modal-close/.modal-body/.modal-footer` (lines 222-231). `competitor_cards.html` currently has **no modal system at all** (full-page view swaps only). Port this exact class structure into `competitor_cards.html` as a small generic `openModal(title, bodyHTML, footerHTML)` / `closeModal()` pair so future modals reuse it too — this is new UI chrome, not a new data system.
- **Bulk Image save mechanics**: existing minimal-patch `apiUpdate({id, property, heroImage})` calls — correct and safe, keep as-is.

## B. Functions/classes to modify

**Hot Fix 1 — button contrast**
- Root cause (confirmed): `.btn-outline` has an **opaque** `background:#fff` (line 68). Several buttons placed on dark backgrounds (`.subject-card-section`, `.compare-bar`, both `background: var(--brand-primary)`) combine class `btn btn-sm btn-outline` with an inline `style="color:#fff;border-color:rgba(255,255,255,0.3)"`, expecting a transparent "ghost" look — but `.btn-outline`'s own white fill wins, producing white-on-white. Not a global `!important` override; confirmed no such rule exists.
- Exact affected buttons: `viewSubjectBtn`, `futureRatesFromGalleryBtn`, `analystBtn`, `collegeHouseBtn` (lines 1079-1082, inside `renderGallery()`'s subject banner) and `acBtn`, `rcBtn`, `clearCompareBtn` (lines 2128-2130, inside `renderComparison()`'s compare-bar).
- Fix: add one new variant class, e.g. `.btn-outline-light` (transparent/translucent bg, white text, translucent white border, proper `:hover`/`:focus-visible`/`:active` states). Replace `btn-outline` + the inline `color:#fff;border-color:rgba(255,255,255,0.3)` on those 7 buttons with `btn-outline-light` and drop the inline style. Leave `.btn-outline` itself unchanged (it's correct for light backgrounds — e.g. `importCardsBtn`, Excel panel Download buttons). Leave `.btn-subject`, `.btn-primary`, `.btn-success`, `.btn-accent`, `.btn-warning` untouched (already correctly readable per the user's own list).

**Hot Fix 2 — Report/Compare checkbox position**
- CSS: `.card-thumb .report-check` / `.card-thumb .compare-check` (lines 123-129). Both are **siblings of `.thumb-img`** positioned absolutely relative to `.card-thumb` (which has variable total height depending on `.thumb-body` content) — currently anchored with `bottom:95px`, which is why the user wants a layout-stable fix rather than more magic numbers.
- Fix: wrap both in one new container `.card-select-group` (single absolutely-positioned flex column: `top:<fixed px inside the 140px image>; right:14px; display:flex; flex-direction:column; gap:6px; align-items:flex-end;`) anchored from the **top** of `.card-thumb` (i.e., inside the fixed-height `.thumb-img`, below `.thumb-badges-right`) instead of `bottom`. Using `top` instead of `bottom` makes position independent of `.thumb-body` height (rate length, name length, missing data) by construction. DOM order inside the group (Report then Compare) — not separate top values — guarantees "Report always directly above Compare."
- HTML change: in `renderGrid()`'s card template (lines 988-989), wrap the two existing `<div class="report-check">…</div>` / `<div class="compare-check">…</div>` blocks in a new `<div class="card-select-group">`. **Do not touch** `data-report-id`/`data-compare-id`, their ids, or the `querySelectorAll('[data-report-id]')` / `[data-compare-id]` handler-attachment code (lines 1025-1046) — purely a wrapper/CSS change.

**Hot Fix 3 — Bulk Update Images property scoping**
- Replace the cross-property loop entirely. Current `loadAllCardsForBulkImages()` calls `/api/properties` then `apiGet(propName)` for every accessible property — this is the bug and should be deleted.
- New approach: build `bulkImageRows` directly from the **already-loaded, already property-scoped** in-memory state: `subjectCard` (if present) + `cards` (both are for `currentProperty` only, per `loadCards()`). No network call needed at all.
- `renderBulkImageTool()`: set subtitle to `currentProperty` (matches "Bulk Update Property Images / The Continuum for UF Grads" example); summary text becomes `<n> record(s) in <currentProperty> competitor set`.
- Add module state `var bulkImageFilter = 'all';` and a filter bar ("All (n) / Missing Image URL (n) / Has Image URL (n)") above the table. Classification uses `row.currentImage` (the stored `heroImage`) trimmed — `missing = !row.currentImage || !row.currentImage.trim()`.
- `renderBulkImageTable()` must render a **filtered view** of the persistent `bulkImageRows` array without ever rebuilding/losing it, so `newValue` typed for a since-filtered-out row survives switching filters and back. Switch row correlation from array-index (`data-bit-input="i"`) to the card's stable `id` (`data-bit-input="<row.id>"`), looking rows up via `bulkImageRows.find(r => r.id === id)` in handlers, since the visible index no longer equals the underlying array index once filtered.
- `saveBulkImageChanges()`: unchanged save semantics (only changed, non-blank `newValue`s; partial `apiUpdate` patch), but after save, re-render the table with the **current filter still applied** (so a saved "Missing" row correctly disappears from the Missing view once its `currentImage` is populated) and recompute filter counts.
- Back button: already calls `renderGallery()` without mutating `currentProperty`/`cards`/`subjectCard` — verify this remains true (no change expected here) so the user lands back in the same active property context.
- Optional (not required): add a defensive `if (!currentUser || currentUser.role !== 'admin') { renderGallery(); return; }` guard at the top of `renderBulkImageTool()`. Not currently reachable any other way (no URL/hash routing exists in this app), so this is hardening only.

**Hot Fix 4 — Rate Compare selection modal**
- New generic modal helpers (`openModal`/`closeModal`) — new, minimal, mirrors `mmp_admin.html`'s existing `.modal-overlay/.modal/...` structure for visual consistency across the product.
- New function `openRateCompareModal()`:
  - Candidate list = `cards.filter(c => c.status !== 'archived')` (same convention as Report Builder Step 1) — already scoped to `currentProperty`, so no cross-property leakage by construction.
  - Row markup reuses `.report-card-item`/`.rci-name`/`.rci-type` plus one more inline field for Starting Rate (`c.startingRate || '—'`).
  - Modal keeps a **local working-copy** selection map, pre-seeded from `compareSelected` filtered to ids present in the candidate list (drops stale ids safely — satisfies the "deleted/stale competitor" edge case without mutating global state until confirmed). Select All / Clear All operate on this working copy and toggle checkbox UI + enable/disable "Compare Selected" live.
  - "Cancel" closes without touching `compareSelected` (so existing per-card Compare checkboxes are unaffected if the user backs out).
  - "Compare Selected" (disabled at 0 selected): commits the working copy into the real `compareSelected` for exactly the candidate ids (so per-card checkboxes on the gallery stay in sync — same underlying store, not a second system), closes the modal, then calls the **existing, unmodified** `renderRateComparison()`.
  - No competitors: render an empty-state message in the modal body instead of a row list; "Compare Selected" stays disabled.
- Wire both existing entry points to the modal instead of calling `renderRateComparison()` directly: gallery toolbar `rateCompareBtn` handler (~line 929) and `renderComparison()`'s `rcBtn` handler (~line 2138). Both become `openRateCompareModal()`.
- Do not modify `renderRateComparison()`, `buildRateCompareHTML()`, or any Rate Comparison rendering/calculation logic. Do not remove the per-card `.compare-check` checkboxes or their handlers (lines 1042-1046) — they remain a valid quick-selection path into the same `compareSelected` state.

## C. Implementation order

1. Hot Fix 1 (pure CSS + class-name swap, zero state/logic risk, quick win).
2. Hot Fix 2 (CSS + one small HTML wrapper change, no JS logic touched).
3. Hot Fix 3 (removes a network loop, reuses existing in-memory state — net reduction in complexity).
4. Hot Fix 4 (introduces the new modal primitive; do last since it's the only fix adding new UI infrastructure, so 1-3 land on a stable base first).

## D. Main regression risks

- **Hot Fix 1**: missing a hover/focus state on the new `.btn-outline-light` variant could make it readable-but-ugly on hover; verify against all three container backgrounds it's used on (subject banner, compare-bar) — both are the same `var(--brand-primary)` navy, so one variant suffices.
- **Hot Fix 2**: `.card-select-group`'s fixed `top` offset must clear `.thumb-badges-right` (impact badge, `top:8px`) at all times, including when both a status badge and impact badge are present — verify visually with a card that has an Impact badge.
- **Hot Fix 3**: switching row identity from array-index to `row.id` in `data-bit-input`/thumbnail-update code must be applied consistently everywhere that attribute is read (input handler, thumbnail refresh, save loop) or edits will silently stop reflecting in the preview.
- **Hot Fix 4**: must confirm `compareSelected` mutations from the modal don't clobber selections for cards NOT in the candidate list — since `compareSelected` is already reset per property switch in this app, in practice it should only ever contain current-property ids, but the commit step should still scope its writes/deletes to the candidate id set defensively.
- General: `reportSelected` and `compareSelected` must remain fully independent through all four fixes (explicit requirement).

## E. Do NOT touch

- `renderRateComparison()`, `buildRateCompareHTML()`, `buildOurPropertyFloorplanDetailHTML()` — rendering/calculation logic for Rate Comparison itself.
- `apiGet`/`apiCreate`/`apiUpdate`/`apiDelete`, `netlify/functions/competitor-cards.js`, `netlify/functions/properties.js` — no backend changes needed for any of the four fixes.
- `data-report-id`/`data-compare-id` attributes, their ids, and their existing change-handler wiring.
- `reportSelected` state and the Report Builder wizard.
- `handleEditCard`/`handleSaveDraft`/`handleSaveComplete` and the rest of the property/competitor edit-save workflow.

## F. Data model impact

**No data model changes required.** All four fixes are UI/state-wiring corrections:
- Hot Fix 3 intentionally uses the **existing** property-name-based relationship (`currentProperty` + `card.property` + already-loaded `cards`/`subjectCard`) rather than introducing the properties collection's `_id` slug into competitor-card documents — that would be a real (out-of-scope) data-model/migration change. Using the in-memory, already-correct `cards`/`subjectCard` for the current property is both simpler and lower-risk than adding a new id relationship, and fully satisfies the reported bug.
- Hot Fix 4 reuses the existing `compareSelected` state as-is (no new field/collection).
